# Astrocyte 商业计划书

**让 AI 研究与创造持续积累。**

个人研究与创造工作台 · 跨 Agent 的项目上下文与经验基础设施

版本：1.0｜编制日期：2026 年 10 月 14 日｜用途：融资沟通与商业规划讨论

本文依据项目规格、实际交付记录和公开资料编制。产品状态截至编制日；市场事实附来源。客户数量、价格、财务预测、融资额度及经营指标均为明确标注的规划假设，尚待项目负责人确认。公司主体、创始团队、实际用户与收入尚未提供核实材料。

## 1. 项目与投资逻辑

Astrocyte 帮助持续使用 AI 开展研究和开发的人，把资料、项目、Agent 会话、成果与经验保存在可持续使用的工作台中。用户能够找回过去的作品，理解当前关注方向，查看判断依据，并将已有工作交给获准的 Agent 继续推进。

产品采用本地优先的方式。资料和业务状态由用户控制；模型调用沿用用户明确选择的客户端与项目许可。Astrocyte 为不同 Agent 提供共享的项目事实和经确认的经验，让工作能够跨会话、跨工具继续。

商业机会来自一个具体问题：用户在 AI 工具上的工作逐渐增多，恢复项目背景、整理交接材料、核对结论和寻找过去成果也持续占用时间。Astrocyte 的付费价值需要体现为更快恢复工作、更可靠地接续项目，以及减少重复整理和核对。

| 事项 | 本计划的判断 |
| --- | --- |
| 首批客户 | 经常切换多个 Agent、同时维护多个项目的独立开发者和研究型开发者 |
| 首个可销售体验 | 找回一件真实作品，查看交接材料，交给指定 Agent，并观察有依据的工作状态 |
| 长期产品定位 | 用户持有的个人认知与工作资产，为不同 Agent 提供持续的上下文 |
| 收入方向 | 官方发行维护、兼容性更新、支持与部署服务；团队业务在满足后续产品条件后开展 |
| 当前阶段 | 已有可运行的工程与真实数据验证，跨 Agent 完整闭环和长期效果验证正在进行 |
| 融资讨论方案 | 人民币 300 万元、18 个月验证窗口；额度和条款待确认 |

投资判断取决于三个结果：用户能否在自己的项目中持续使用、能否观察到可重复的工作收益、是否愿意为维护和服务持续付费。目前已有技术证据，商业证据仍需建立。

## 2. 用户问题与使用场景

### 2.1 第一类客户

首批客户应同时具备三个特征：每周多次使用 AI 研究或开发；维护多个持续数周以上的项目；存在更换 Agent、恢复旧项目或复用经验的需求。这一人群有完整工作记录，可以验证产品是否改善实际流程。

| 用户 | 具体问题 | Astrocyte 提供的价值 | 购买理由 |
| --- | --- | --- | --- |
| 独立开发者 | 旧项目分散在目录、分支和聊天记录中，重新开始前需要查找背景 | 作品总览、文件核实、交接材料与项目证据 | 缩短恢复项目的时间 |
| 研究型开发者 | 论文、视频和实现过程彼此分离，结论难以回到项目中使用 | 固定版本资料、主题关联、项目上下文和经验记录 | 减少重复阅读与整理 |
| 经常切换 Agent 的用户 | 原会话与新会话之间存在背景、约束和成果缺失 | 区分原生接续与上下文交接，展示来源和未完成事项 | 降低交接遗漏和重复解释 |
| 后续团队客户 | 成员与 Agent 交替参与，决策依据和有效经验容易丢失 | 受控分享、部署维护与兼容性服务 | 让工作连续性能够被团队管理 |

团队客户属于后续扩展。当前首版范围为单用户、单台机器，团队多用户与跨设备能力需要独立设计和验收。

### 2.2 三个高频场景

**恢复一个停了两周的项目。** 用户打开作品列表，核实代码目录，查看最后一次成果、失败和下一步，选择 Agent 继续。产品价值通过准备时间、遗漏情况与接续结果衡量。

**将一项研究转成可执行改进。** 用户导入论文或视频资料，查看来源、关联与缺少的依据，形成范围明确的项目提案。资料准入和执行批准分别由用户控制；完整研究到执行流程仍需后续验收。

**让另一名 Agent 接手工作。** 用户选择作品与交接方式，确认项目权限。平台保留原会话或交接上下文的身份，展示执行状态、结果和证据。换工具时已有成果能够继续被使用。

上述场景描述产品目标，实际交付状态见第 4 节。

## 3. 产品方案

### 3.1 产品结构

| 模块 | 用户需要回答的问题 | 核心内容 |
| --- | --- | --- |
| Attention：资料与认知 | 我最近在关注什么，有哪些依据和可复用经验？ | 资料整理、认知事件、关注演化、知识与经验确认 |
| Workspace：作品与工作区 | 我的作品在哪里，当前做到哪里，下一步交给谁？ | 项目身份、作品总览、交接材料、原生会话与权限 |
| Swarm：协作执行方向 | 如何在批准范围内开展协作并采用成果？ | 范围明确的任务、协作和结果回流；完整能力仍属后续开发 |

产品规格的完整流程是：收藏资料 → 整理与关联 → 筛选候选 → 人工准入 → 提案与批准 → Agent 执行 → 成果与经验回流。近期销售验证聚焦作品恢复与接续，后续扩展沿既有规格推进。

### 3.2 用户持有的长期资产

Astrocyte 保存资料的来源和版本、项目的真实身份、事件证据、人工确认的知识与经验，以及关键决定的来源。每次会话结束后，这些资产仍可供后续工作使用。

认知状态用于帮助用户判断当前焦点，实际事件提供回查依据。知识事实版本采用只追加语义，避免新整理覆盖旧版本。跨项目知识与经验使用需要人工显式分享。

### 3.3 用户控制与数据边界

产品默认从明确登记、批准的资料和项目范围获取信息。用户决定读取范围、模型处理许可及执行授权；Agent 查询与系统刷新记录为机器使用，避免将其自动解释成人类兴趣。

本地运行的 CLI 可能调用外部模型。产品需要显示实际客户端和已知模型信息，按项目许可交付上下文。当前系统的控制边界与原生客户端有关，同机操作系统级进程隔离仍有实际限制。

### 4.2 真实实验说明

V4 实验比较三种输入：A 使用认知状态、可回溯的派生证据和已批准经验；B 使用最近七天完整聊天；C 不使用记忆。三组使用相同模型配置和题目。

结果适用范围严格限定为该用户、该日及两道事实题。A 包含当天 Git 事实，B 的输入限定为最近七天聊天；当天授权原生会话来源没有新增认知事件，两组来源不同。A 在活跃项目题中召回了两个真实项目中的一个。当前不能将分数用于宣称普遍优于长上下文，或计算商业效率提升。

七日最终结果、用户原因评分及 D+3 预测对账仍未完成。首日 approved 经验数量为 0，因此这一日的结果无法证明经验复用带来的增益。

## 5. 市场机会

### 5.1 需求背景

Stack Overflow 2025 年调查中，84% 的受访者正在使用或计划使用 AI 开发工具，51% 的专业开发者每日使用；46% 的受访者不信任其输出准确性。Agent 影响问题中，只有 17% 认可其改善团队协作。这些数据支持研究工作连续性、核验与协作需求；调查各问题的样本不同，不能据此推算多 Agent 付费市场规模。[官方调查](https://survey.stackoverflow.co/2025/ai)

Astrocyte 的机会判断是：AI 使用越频繁，项目背景、成果来源和长期经验的管理越可能成为独立需求。是否形成付费需求，需要通过实际恢复和交接任务验证。

### 5.2 首批市场范围

近期市场聚焦中国及能够服务的海外开发者社区，优先覆盖使用多个 Agent 的独立开发者与研究型开发者。进入顺序依据客户问题强度、现有客户端适配和支持能力决定。

满足以下条件的人才计入初期可服务客户：使用已支持的客户端与环境；愿意登记明确项目；存在重复恢复或交接需求；具备付费意愿。普通 AI 使用者不直接计入这一范围。

### 5.3 从客户数计算市场容量

目前缺少可核实的目标客户总数，以下仅提供计算方法。假设每个付费账户年均净收入为 900 元：

| 可服务且愿意付费的账户数假设 | 对应年收入容量 | 使用含义 |
| ---: | ---: | --- |
| 10,000 | 900 万元 | 初期细分市场测算 |
| 30,000 | 2,700 万元 | 扩大社区与客户端覆盖后的测算 |
| 100,000 | 9,000 万元 | 更广地域与使用场景的测算 |

账户数均为假设，尚未证明可触达或可转化。该表属于市场容量敏感性计算。后续以实际渠道触达量、目标用户占比、激活率和付费率替换假设。

第三年情景目标为 6,000 个期末付费账户。在 30,000 个目标账户的假设下，这意味着 20% 覆盖率，要求较高，需要用实际渠道结果验证。长期扩展空间包括团队部署与组织知识连续性，但当前没有可核实的团队市场规模。

## 6. 竞争与差异

| 产品或替代方式 | 已满足的主要需求 | Astrocyte 需要证明的购买价值 |
| --- | --- | --- |
| Cursor 等 AI 开发工具 | 编码、Agent 执行、项目开发与评审 | 用户切换客户端后，作品、上下文和经验仍能持续使用 |
| Obsidian 等知识工具 | 知识记录与组织；Obsidian 核心应用可免费使用 | 将资料与真实项目、会话和执行结果连起来，减少人工交接维护 |
| Mem0 / OpenMemory 等记忆基础设施 | 持续记忆、检索与 Agent 集成，已有免费和收费服务 | 直接面向个人工作的作品恢复、证据与交接体验 |
| 手工维护 README、状态文件与聊天记录 | 低成本保存背景、决定和操作说明 | 减少整理时间，并保持文件、项目和会话身份可核实 |

竞品能力依据：[Cursor 官方产品介绍](https://cursor.com/en-US)、[Obsidian 官方定价](https://obsidian.md/pricing)、[Mem0 官方服务](https://mem0.ai/pricing)。上述产品持续演进，比较关注用户购买价值，不将未调研的能力记为缺失。

Mem0 的官方 Starter 价格为 19 美元/月，Pro 为 249 美元/月，按不同请求量与能力分层。这表明记忆维护存在收费产品，不能直接证明 Astrocyte 的定价或个人用户付费意愿。[Mem0 官方定价，2026-10-14 查阅](https://mem0.ai/pricing)

Astrocyte 的差异集中在四项组合：用户控制的本地资产、跨 Agent 工作连续性、可回溯的认知与经验，以及作品到接续工作的直接入口。成熟工具可能扩展这些能力，项目需要持续证明组合体验带来的独立收益。

### 6.1 可以持续积累的竞争优势

**兼容性与维护经验。** 不同客户端具有各自的原生会话、能力和权限边界。持续处理真实升级与交接问题，可以形成稳定的兼容记录和支持流程，直接提高官方维护服务的价值。

**用户自己的工作资产。** 来源、成果、人工确认的知识和经验持续被使用，有机会形成长期工作习惯。资产由用户控制，跨项目分享遵循明确许可；当前没有授权将私人资产汇集成公共训练数据。

**真实案例与服务信誉。** 不同环境下的恢复成功、接续结果和问题处理记录能够帮助用户判断产品是否适用，并降低后续销售与支持成本。对外案例需要用户许可，保留可核实的范围和结果。

上述优势需要在持续交付和客户使用中形成。现阶段已有工程与内部验证基础，尚无足够的商业客户证据证明长期竞争优势。

## 7. 商业模式与定价方案

### 7.1 收入结构

仓库当前包含 AGPL v3 许可证。收费方案围绕官方发行维护、兼容性更新、支持及部署服务设计；发行、托管、贡献者权利和第三方依赖的具体商业安排需要核实。当前尚未确认替代许可证或额外商业授权。

| 产品与服务 | 规划价格 | 服务内容与条件 |
| --- | ---: | --- |
| 社区自部署 | 免费 | 按现有许可证使用源码，提供公开文档与社区交流 |
| 官方维护服务 | 99 元/月或 999 元/年 | 官方发行包、兼容性维护、升级协助与有边界的技术支持；正式内容待确认 |
| 部署与迁移服务 | 按范围报价 | 环境配置、客户明确选择的项目迁移与培训，以实际交付范围核价 |
| 团队维护服务 | 后续核价 | 多用户与分享能力完成后，提供组织部署和维护 |

以上价格属于商业验证方案，尚未上线。财务情景仅计个人官方维护服务；部署与团队收入在取得实际合同前不计入。

### 7.2 为什么持续付费

付费服务需要承担客户端协议变化、安装与升级、原生会话兼容、故障处理和使用支持。用户可以自行维护，官方服务以节省维护时间和保证持续可用性获得收入。

产品长期留存依赖资料、项目与经验持续被使用。已有资产越丰富，恢复和交接越有价值；用户仍应保有数据与迁移选择。迁移成本来自已经形成的工作习惯和服务价值。

### 7.3 模型费用与成本责任

用户沿用其已配置的模型账户，模型及原生 Agent 费用由用户承担，授权入口应显示这一安排。平台自身的研发、兼容验证和支持模型调用进入公司费用。本地部署仍需要安装、升级与支持，服务成本必须按实际使用计量。

如后续提供平台代付推理，应单独制定用量、账单与限额方案，并重算财务模型。当前情景没有包含平台承担的大规模客户推理成本。

## 8. 客户获取与增长

### 8.1 从真实项目试用进入市场

第一批客户通过项目作者直接招募，优先选择能够展示真实项目恢复与 Agent 交接需求的用户。试用以用户授权的实际项目为基础，记录安装问题、恢复过程、结果与付费决定。

对外展示围绕一个可理解的过程：打开旧作品，查看背景，选择 Agent，接续工作，并查看来源明确的事件。三分钟体验属于已规定的产品目标，需要完整验收后作为正式销售演示。

### 8.2 渠道安排

| 渠道 | 内容与动作 | 成效指标 |
| --- | --- | --- |
| 开发者社区与开源项目 | 发布真实恢复案例、安装说明和兼容性记录 | 合格试用人数、安装成功率与激活率 |
| Agent 使用者社区 | 演示不同客户端之间的项目接续 | 完成交接人数、重复使用频率 |
| 研究与开发内容 | 展示论文来源、项目改进与结果回查 | 目标用户线索与实际试用转化 |
| 用户推荐 | 在用户取得持续收益后邀请推荐 | 推荐付费人数与获客成本 |

现阶段没有已签署的渠道伙伴。大额广告支出应以客户留存、支付与单位经济的实际结果为条件。

### 8.3 销售与留存流程

合格用户试用 → 安装并登记一个明确项目 → 恢复或接续一次真实工作 → 次周再次使用 → 购买维护服务 → 持续获得升级和支持。

试用阶段以完成实际任务为目标。收费前需要明确服务范围、支持时限、数据处理说明和用户退出方式；相关页面与交易系统尚未作为当前功能交付。

## 9. 商业验证与里程碑

以下指标为建议的商业验收目标，尚待负责人确认。经营周期从产品满足对外试用条件后开始，不改变已有 V4 日程或冻结规则。

| 阶段 | 必须完成的事情 | 建议验收目标 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| 对外试用前 | 完成当前 L1 真实闭环、Workbench 剩余验收、既定长期验证；确定服务及数据边界 | 原任务验收全部按既定标准完成 | 具备可重复演示与可支持的发行包 |
| 第 1–3 个月 | 与 20 名合格用户测试真实项目恢复和接续 | 至少 12 人独立激活；激活用户第 4 周留存不低于 50%；形成至少 5 个可核实案例 | 用户重复使用，问题可归因并能解决 |
| 第 4–9 个月 | 上线维护服务与支付，验证价格与支持成本 | 累计至少 100 名实际付款客户；支持成本与续订数据可核对 | 实际付款、服务交付和持续使用同时成立 |
| 第 10–18 个月 | 扩大兼容覆盖和有效渠道，形成稳定发行与支持流程 | 付费流失和获客成本达到第 10 节经营条件 | 增长后的单位经济仍可接受 |

这些目标属于拟议的商业计划，不能将未完成目标记录为结果。第 11 节三年收入情景还要求更大的获客规模。

**激活口径：** 用户完成登记自己的项目，查看有来源的交接材料，并成功完成一次真实恢复或接续任务。仅安装、打开页面或生成摘要不计为激活。

**留存口径：** 按首次激活周划分用户，第 4 周至少完成一次上述有效工作。分母固定为该批激活用户，不能只保留仍有活动的人。

**效率口径：** 比较同一用户相近任务的准备与核对时间，同时记录遗漏、返工和最终结果。节省时间只有在质量保持的情况下才算收益；具体改善目标待首批真实数据建立后确认。

经营指标的采集应沿明确授权进行，说明具体内容与用途；当前不推导额外采集用户私人材料的许可。

## 10. 单位经济模型

以下为个人维护服务的测算输入，全部属于假设，尚未由实际支付与成本验证。

| 输入 | 情景值 | 口径 |
| --- | ---: | --- |
| 年均净收入 | 900 元/付费账户 | 将折扣、退款和支付损耗折算后的年均收入，区别于 999 元标价 |
| 年均可变服务成本 | 90 元/付费账户 | 随账户增长的服务成本；固定支持人员费用另列 |
| 年均贡献 | 810 元/付费账户 | 900−90 |
| 贡献率 | 90% | 810÷900；未扣固定研发、支持、渠道和管理费用 |
| 按月折算贡献 | 67.5 元/账户 | 810÷12 |
| 新付费客户获客成本上限 | 250 元 | 渠道、推广与可归属销售成本÷新付费客户数 |
| 月度付费流失情景 | 3% | 用于可按月取消的订阅测算；年付客户需单独按到期续费衡量 |

在上述假设下，简化的获客回收期为 250÷67.5≈3.7 个月。稳定月流失情景下，未折现的贡献生命周期价值为 67.5÷3%≈2,250 元，约为获客成本的 9 倍。该算法未计价格变化、服务扩张、固定费用及年付差异，不能作为实测 LTV。

若月流失升至 8%，同一算法得到约 844 元，LTV/CAC 约 3.4。若获客成本同时升至 400 元，比值约 2.1，需要改善留存、成本或定价后再扩大支出。

正式经营应分渠道记录获客成本，按月付与年付分别记录流失与续费；至少经过真实付费周期后再更新模型。

## 11. 三年收入与支出情景

### 11.1 测算假设

以正式收费后的三个经营年计算，货币单位均为人民币。收入按服务期间计算；将年度经营净额近似用于融资讨论，不构成完整现金流或会计报表。年付预收、税费、应收账款、资本支出和融资成本尚未建模。

首年假设期末 500 名付费客户、全年平均 150 名，收入主要来自年内较晚获客；第二年平均 1,000 名、期末 2,000 名；第三年平均 3,500 名、期末 6,000 名。平均数已经包含加入和流失的综合影响，具体月度客户曲线待实测数据建立后补充。

### 11.3 盈亏平衡条件

按第三年固定支出 390 万元、每账户年贡献 810 元计算，需要全年平均约 4,815 个付费账户才能覆盖固定经营支出。该条件高于第三年 3,500 个平均账户假设，因此本情景第三年仍亏损。

第三年期末 6,000 个账户对应按月折算的收入运行规模为 45 万元/月，按年折算为 540 万元。运行规模基于期末账户，区别于当年按平均账户计算的 315 万元服务收入。

| 第三年敏感性情景 | 服务收入 | 服务贡献 | 经营净额 |
| --- | ---: | ---: | ---: |
| 平均客户为基准的 50%：1,750 人 | 157.50 | 141.75 | −248.25 |
| 基准：3,500 人 | 315.00 | 283.50 | −106.50 |
| 平均客户为基准的 150%：5,250 人 | 472.50 | 425.25 | 35.25 |

敏感性表固定每账户收入、可变成本与 390 万元固定支出，未假设收入增长一定不增加人员成本。实际人员与服务负荷变化需要重算。

## 12. 融资方案与资金用途

本计划提出 **300 万元人民币、18 个月**的融资讨论情景，尚未形成已确认的融资需求。估值、融资工具、出让比例、公司主体与投资人条件均待项目负责人决定。

## 14. 主要风险与应对

| 风险 | 可能影响 | 经营和产品措施 |
| --- | --- | --- |
| 用户需求频率不足 | 用户偶尔使用，难以持续订阅 | 优先招募多项目、多客户端用户，按真实任务验证第 4 周留存 |
| 已有工具快速扩展 | 单一工具内可完成更多上下文和协作管理 | 持续验证跨客户端价值，保持用户资产和接入方式清晰 |
| 原生协议与配置变化 | 接续失效、支持成本上升 | 保存兼容版本与能力状态，对未验证能力显示未知，固定负责人维护 |
| 效果证据不足 | 技术成绩无法转化为购买理由 | 完成既定长期验证，并增加不同用户的真实任务和付费记录 |
| 数据与工具权限错误 | 错误读取、外发或修改用户资产 | 保持项目隔离、明确许可、动作回执和来源回查，按具体执行路径验证 |
| 自部署替代付费服务 | 用户选择自行安装维护 | 用发行质量、升级和支持收益证明持续服务价值 |
| 支持负荷超过假设 | 每账户成本升高，贡献率下降 | 计量安装、兼容和问题处理成本，重算套餐与服务边界 |
| 增长慢于情景 | 融资可用期缩短，无法覆盖长期研发 | 按实际现金与留存安排支出，优先完成可核实的客户收益 |
| 授权与商业安排未核实 | 影响发行、托管和后续合同 | 明确源码、贡献和依赖权利，核实商业条款后再对外签约 |

### C. 财务公式

18 个月经营资金净需求＝第一年支出＋第二年支出的一半−第一年收入−第二年收入的一半；该公式采用第二年金额均匀分布的假设。
